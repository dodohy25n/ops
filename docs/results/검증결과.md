서빙 경로는 서버와 같은 `parse_csv` → 정렬 → `encode` → 저장된 스케일러 → 20건 묶기 순서로 만들었습니다.
원본 분기 파일 32개를 업로드처럼 **파일마다 따로** 변환했기 때문에, 파일마다 각 카드의 첫 19건은 이력이 부족해 판정 대상에서 빠집니다. 그래서 시퀀스가 1,281,085개입니다. 전체 파일을 합쳐 한 번에 만들 때의 시퀀스 수 1,904,014개([발표 노트](../발표노트.md) 1절)보다 적은 이유가 이것이며, 비교한 1,281,085개는 모두 최대 차이 0이었습니다.

이 비교에서 업로드 검사가 한도 빈칸을 거부하던 문제와 승인시간대 문자열 정렬로 서빙에서만 거래 순서가 뒤집히던 문제를 찾아 고쳤습니다.

확인한 것:

- PSI 경고만 있고 성능이 유지된 명절 구간에서는 재학습하지 않았습니다. 명절 주입(9/13~9/19) 창 97~104는 모두 PSI 경고(금액 PSI 1.548~1.582)였고, 9월 재학습 요청은 그 이전인 95번째 창(9/11~9/12 거래)에서 나왔습니다.
- 창별 기록과 이벤트는 같은 실행의 감시 파일로 남겼습니다: [windows-v1.jsonl](시연-감시-기록/windows-v1.jsonl)(v1 창 1~157), [windows-v4.jsonl](시연-감시-기록/windows-v4.jsonl)(교체 후 v4 창 75개), [events.jsonl](시연-감시-기록/events.jsonl)(이벤트 18개: PSI 알림, 재학습 요청·미달·통과, 판정 창 초기화).
- 게이트가 후보 3개 중 2개를 떨어뜨렸고, 떨어진 경우 v1이 계속 판정했습니다.
- 통과한 v4는 서버 재시작 없이 다음 분석(11월)부터 판정에 쓰였고, 판정 창이 초기화됐습니다(이벤트 `window_reset` 1 → 4).
- 재학습의 fine-tune·τ·홀드아웃은 시간순 건수(24,000 / 8,000 / 8,000)로 나눕니다. 같은 거래는 두 구간에 들어가지 않습니다. 건수로 나누므로 경계일 하루는 두 구간에 나뉠 수 있습니다(예: 7월 fine-tune 끝 7/19 = τ 시작 7/19).
- 재학습은 seed와 TensorFlow 연산 결정성을 고정했습니다. 개발자가 같은 조건으로 전체 시연을 두 번 실행해 같은 결과를 확인했습니다(두 번째 실행 로그는 저장소에 없음).

## 테스트 45개

다음 테스트는 모두 통과했습니다(`Ran 45 tests ... OK`, 커밋 `a3be830`). 구성은 CSV/API 15, 배포 게이트 9, 판정 창 감시와 시간 분할 8, 분석 API 감시 연결과 재시작 복구 7, PSI 3, 재학습 통합 2, Registry 흐름 1입니다. Registry·재학습 통합 테스트는 별도의 임시 DB와 합성 시험용 모델로 실행했습니다.

### 판정 창 감시와 재학습 분할

| 테스트 | 검증한 동작 |
|---|---|
| windows_close_every_window_size | 창 크기만큼 쌓일 때마다 창이 닫히고, 남은 건수는 다음 분석으로 넘어갑니다 |
| trigger_at_second_consecutive_window_even_if_later_window_recovers | 두 번째 연속 미달 창에서 요청하며, 같은 분석의 뒤쪽 정상 창이 요청을 지우지 않습니다 |
| insufficient_window_holds_counter | 판정 보류 창은 연속 횟수를 유지합니다 |
| no_second_request_while_waiting_and_rejection_resets | 재학습을 기다리는 동안 다시 요청하지 않고, 게이트 미달 후 연속 횟수를 비웁니다 |
| duplicates_are_skipped | 같은 거래를 다시 넣으면 건너뜁니다 |
| new_champion_resets_windows_and_keeps_old_records | 운영 모델이 바뀌면 창을 초기화하고 이전 기록을 `observations-v1.csv`로 보관합니다 |
| psi_alert_is_logged_without_retrain | PSI 경고는 이벤트만 남기고 재학습을 요청하지 않습니다 |
| time_split_is_ordered_and_disjoint | 40,000건을 시간순 건수로 24,000 / 8,000 / 8,000으로 나누고, 같은 거래가 두 구간에 들어가지 않습니다 |

### 재학습 통합과 분석 API 감시 연결

임시 `FRAUD_API_DIR`·`FRAUD_MLFLOW_DIR`와 합성 시험용 모델로 실행합니다. 실제 학습 성능을 뜻하지 않습니다.

| 테스트 | 검증한 동작 |
|---|---|
| candidate_passing_gate_becomes_champion_and_resets_monitoring | `retrain.run` 한 번으로 후보 등록 → 게이트 통과 → champion 이동(`gate_passed=true`) → 서버 로더가 새 버전·τ 사용 → 이벤트 `retrain_promoted`와 세 구간의 시간 순서 확인 → 다음 분석에서 감시 상태가 새 버전으로 초기화되고 이전 기록이 `observations-v1.csv`·`windows-v1.jsonl`로 보관됨 |

## 재현

데이터 준비와 스케일러 생성, v1 학습 이후 프로젝트 최상위 폴더에서 실행합니다.

```bash
python -m unittest discover -s backend/tests -t . -v
python -m backend.serving_app.train_and_register
```

등록 명령은 v1을 버전 1로 등록하고 `champion`으로 지정합니다. 이미 운영 모델이 있으면 거부합니다. 테스트 통과는 프로그램의 제어 흐름이 맞다는 결과이고, 실제 fine-tuning과 게이트 교체는 위 6개월 시연으로 확인했습니다. 시연 재현 명령은 [CSV 서버 가이드](../FastAPI-CSV서버.md#6개월-시연-실행)에 있습니다.

## Docker 컨테이너 시연

로컬과 컨테이너의 판정 일치(43,503건, [CSV 서버 가이드](../FastAPI-CSV서버.md) 검증 절)는 감시 연결 이전 커밋에서 확인했습니다. 감시·재학습을 연결한 뒤에는 새 볼륨의 `model-runtime` 컨테이너에 v1을 등록하고, `run_demo.py --api http://127.0.0.1:8099`로 6개월 시연 전체를 HTTP로 다시 돌렸습니다. 월별 결과(7월 v2 미달, 9월 v3 미달, 10월 v4 통과 Recall 0.953, 11·12월 Recall 0.964·0.958)가 위 시연 로그와 같았습니다. 출력 전체는 [Docker 시연 로그](시연-실행-로그-docker.txt)에 있습니다(`demo_docker.sh` 실행, Linux arm64). 시연 부분은 약 37초 걸렸으나 시간은 기록 파일에 남지 않았습니다.
