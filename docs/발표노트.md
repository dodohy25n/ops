# 발표 노트

> 단계마다 발표에 넣을 핵심만 쌓습니다. 자세한 근거는 [데이터분석.md](데이터분석.md), [설계지표.md](설계지표.md)에 있습니다.

## 1. 데이터 준비

**데이터**
- AI Hub 카드거래 합성데이터, 2021~2024년, 1,952,871건, 이상거래 3.69%, 카드 2,636장

**LSTM을 쓰는 근거 (실측)**
- 직전 거래가 이상거래면 이번 거래도 이상일 비율 42.9%, 직전이 정상이면 2.2%
- 가장 많은 유형(카드 위변조, 44.6%)은 "최근 거래 패턴 대비 금액 급증"으로 정의되며, 실제 금액이 직전 10건 평균의 6.13배
- 예시: 4천~9천 원씩 쓰던 카드가 저녁 7시에 145만 9천 원 결제 → 이상거래

**전처리**
- 거래 한 건을 숫자 17개로 변환 (금액, 시간대, 해외 여부, 가맹점 특성, 할부, 카드 종류)
- 정답이 담긴 `이상거래유형`, `이상거래설명` 컬럼은 제외
- 카드별 최근 20건을 묶어 시퀀스 1,904,014개 생성

**시간 기준 분할**
- 제공된 Training/Validation은 같은 기간에서 무작위로 나뉘어 있어 미래 정보가 학습에 섞입니다. 그래서 두 파일을 합쳐 시간 기준으로 다시 나눴습니다.

| 구간 | 기간 | 시퀀스 | 용도 |
|---|---|---|---|
| train | 2021~2023 | 1,436,555 | v1 학습 |
| valid | 2024 상반기 | 235,562 | 기준값 측정 |
| ops | 2024 하반기 | 231,897 | 운영 시연, 드리프트 주입 |

**학습과 서빙의 일치**
- 변환 규칙을 `data/features.py` 한 곳에서 관리하고, 스케일러는 학습 기간으로 한 번만 fit해 저장합니다.
- 원본 거래 1,952,871건 전체를 서버와 같은 경로(`parse_csv` → 정렬 → `encode` → 저장된 스케일러 → 20건 묶기)로 변환해 학습 입력과 비교했습니다. 시퀀스 1,281,085개에서 최대 차이 0이었습니다([검증 결과](results/검증결과.md)).
- 1,281,085개가 위의 1,904,014개보다 적은 이유는 원본 분기 파일 32개를 업로드처럼 파일마다 따로 변환해, 파일마다 각 카드의 첫 19건이 이력 부족으로 빠지기 때문입니다.
- 이 비교에서 서빙에서만 승인시간대를 문자열로 정렬해 "7"이 "15"보다 뒤에 놓이던 문제와, 업로드 검사가 카드 한도 빈칸을 거부하던 문제를 찾아 고쳤습니다.

**막힌 것 → 해결**
- 가맹점 전월 매출에 음수(취소 초과)가 약 1,500건 있었고, 로그 변환에서 무한대가 생겨 해당 컬럼 전체가 NaN이 되었습니다(검증 데이터에서 471만 개). 에러 없이 학습이 진행될 수 있는 "조용한 실패"였습니다.
- 음수를 0으로 처리하고, 피처에 NaN이나 무한대가 있으면 즉시 에러를 내도록 막았습니다.

## 2. v1 학습과 기준값 측정

**모델**
- HAIC의 LSTM 구조(32 → 32 → 16)를 유지하고, 출력만 종가(회귀)에서 이상거래 확률(sigmoid, binary crossentropy)로 바꿨습니다.
- 2021~2023년 시퀀스 1,436,555개로 학습했습니다. 학습 데이터에서 떼어 둔 카드 10%의 PR-AUC가 2 epoch 연속 나아지지 않으면 멈추도록 했습니다. 실제로는 마지막까지 조금씩 올라(epoch 9 0.938 → epoch 15 0.943) 상한인 15 epoch에서 끝났고, 505초가 걸렸습니다.

**v1 성능 (2024년 상반기, 학습에 쓰지 않은 기간)**

| 지표 | 값 |
|---|---|
| τ (F2 최대) | 0.28 |
| F2 | 0.909 |
| Recall | 0.952 |
| Precision | 0.770 |
| PR-AUC | 0.942 (아무 학습 없는 기준선 0.036) |
| 경보 비율 | 4.45% |

**측정으로 정한 운영 기준**

| 기준 | 값 | 근거 |
|---|---|---|
| β | 2 | 이상거래 평균 금액 104만 원, 정상 2만 5천 원 (약 42배) |
| 게이트 R_min | 0.95 | v1 Recall 내림 |
| 게이트 경보 비율 | 6% 이하 | 탐지팀 처리량을 가정했습니다. P_min 0.57은 참고 계산값으로만 남깁니다 |
| Precision 트리거 | 0.629 미만 2개 창 연속 | 정상 창 평균 0.769 − 2 × 0.070 |
| Recall 트리거 | 0.863 미만 2개 창 연속 | 정상 창 평균 0.951 − 2 × 0.044 |
| PSI | 0.1 주의, 0.25 경고 | 정상 창 최댓값 0.079로 정상 기간에는 울리지 않음 |

**β = 2를 고른 이유 (β 1~5 비교, `scripts/compare_beta.py`)**

| β | τ | 놓친 사기 | 잘못 막은 정상 | 경보 비율 | 사기 1건 더 잡는 대가 |
|---|---|---|---|---|---|
| 1 | 0.49 | 862 | 1,357 | 3.81% | |
| **2** | **0.28** | **408** | **2,409** | **4.45%** | 정상 2.3명 |
| 3 | 0.16 | 188 | 3,849 | 5.15% | 정상 6.5명 |
| 4 | 0.11 | 120 | 4,732 | 5.56% | 정상 13.0명 |
| 5 | 0.06 | 59 | 5,979 | 6.11% (상한 초과) | 정상 20.4명 |

- 1 → 2: 정상 고객 2.3명 확인으로 사기 1건(평균 104만 원)을 더 잡으므로 확실히 이득입니다.
- 2 → 3 이상: 대가가 6.5명, 13명, 20명으로 커지고, 경보 상한 6%까지 남는 여유가 1.55%p에서 0.85%p 이하로 줄어 명절이나 드리프트 때 경보가 넘칠 수 있습니다.
- β는 "무엇이 더 중요한가"를 정하는 기준이라 점수가 가장 높은 β를 고를 수는 없습니다. 그래서 β별로 얻는 것과 잃는 것을 비교해 정했습니다.

**측정으로 바뀐 설계**
- 처음에는 PSI 경고 시 트리거 기준을 −1σ로 좁히려 했습니다. 하지만 정상 6개월에 적용하면 잘못된 재학습이 15회 발생해서 이 규칙을 뺐습니다.
- −2σ와 2개 창 연속 조건은 같은 기간에 잘못된 재학습이 0회였습니다. 기준 아래로 떨어진 창은 13개 있었지만 두 창이 연달아 떨어진 적은 없었으므로, 연속 조건이 오탐을 막는 핵심입니다.
- PSI를 처음에는 모든 피처에 분위수 구간으로 계산해, 해외·할부처럼 0이 대부분인 피처는 비율이 1%에서 50%로 바뀌어도 PSI가 0이었습니다. 범주형은 값별 비율로 계산하도록 고치고 기준 분포를 다시 쟀습니다. 재측정한 정상 창 PSI 최댓값은 모두 0.1 미만(최대 시간대 0.079)이고, τ와 게이트·트리거 기준은 그대로입니다.


## 3. MLflow 기록과 배포 게이트

- 기존 v1을 재학습하지 않고 MLflow에 기록했습니다. 모델, 스케일러, τ와 운영 기준을 같은 실행에 묶었습니다.
- v1은 운영을 시작하는 기준 모델이므로 Registry 버전 1로 등록하고 바로 `champion`으로 지정했습니다.
- 배포 게이트는 재학습한 후보 v2를 내보내도 되는지 판단하는 장치입니다. v2와 운영 모델을 fine-tuning에 쓰지 않은 같은 최근 홀드아웃에서 비교합니다.
- 게이트는 F2 회귀 없음, Recall ≥ 0.95, 경보 비율 ≤ 6%를 검사합니다. 하나라도 실패하면 기존 운영 모델을 유지합니다.

**검증 증거와 발표 포인트**

- MLflow에서 다시 불러온 운영 모델은 상반기 검증 시퀀스 20,000건에서 로컬 v1과 점수 차이 0, 판정이 모두 일치했습니다.
- 원본 32개 파일 전체를 서버와 같은 경로로 변환해 학습 입력과 비교했습니다. 이 과정에서 서빙에서만 거래 순서가 뒤집히던 정렬 문제를 찾아 고쳤고, 수정 후 1,281,085개 시퀀스가 학습 입력과 완전히 일치했습니다. 파일마다 따로 변환해 파일별로 카드의 첫 19건이 빠지므로, 전체를 합친 시퀀스 수 1,904,014개보다 적습니다.
- 합성 시험용 모델과 임시 DB로 기준 모델 등록, 실패 후보의 운영 교체 차단, 성공 후보의 모델·τ 교체, 재로딩 실패 시 캐시 유지까지 검증했습니다. 실제 재학습 성능은 4절의 6개월 시연으로 확인했습니다.

## 4. 운영 감시·재학습과 6개월 시연

**연결한 흐름**
- CSV 분석마다 판정 거래를 날짜 → 카드 순으로 쌓아 1,000건마다 창을 닫고 Precision·Recall·PSI를 계산합니다(`monitoring/drift_monitor.py`).
- PSI는 알림만 남깁니다. Precision 또는 Recall이 평균 − 2σ 아래로 2개 창 연속이면 응답 뒤 백그라운드에서 재학습합니다.
- 재학습은 champion에서 이어서 학습합니다. 정답 있는 최근 40,000건을 시간순 60%(fine-tune) · 20%(τ 선택) · 20%(게이트 홀드아웃)로 나눕니다(`retrain.py`).
- 게이트를 통과하면 champion이 옮겨지고, 서버는 재시작 없이 다음 분석부터 새 모델을 씁니다. 판정 창도 처음부터 다시 셉니다.
- 재학습 도중 서버가 꺼지면 다음 시작 때 그 재학습을 「실패(서버 재시작으로 중단)」로 정리해, 이후 하락 때 다시 요청할 수 있게 했습니다.
- 시연은 `bash backend/scripts/demo_docker.sh` 한 번으로 컨테이너에서 실행합니다. 컨테이너 결과도 로컬 시연 로그와 월별로 같았습니다([검증 결과](results/검증결과.md#docker-컨테이너-시연)).

**시연 결과 ([시연 실행 로그](results/시연-실행-로그.txt))**

| 월 | 장면 | 판정 모델 | Recall | 무슨 일이 있었나 |
|---|---|---|---|---|
| 7월 | ① 정상(실제) | v1 | 0.910 | 실제 데이터에서 Recall이 2개 창 연속 미달 → 후보 v2는 F2가 더 높았지만(0.866 대 0.839) Recall 0.923으로 하한 미달 → v1 유지 |

**막힌 것 → 해결**
- 판정 거래를 시간대 순으로 묶었더니 창 하나가 몇 시간치 거래만 담아 정상 데이터에서도 PSI가 울렸습니다. 기준값을 잴 때와 같이 날짜 → 카드 순으로 바꿨습니다.
- 연속 조건을 CSV 분석이 끝난 뒤 한 번만 확인했더니, 뒤쪽 정상 창이 연속 횟수를 지워 10월(미달 창 29개)에도 재학습이 요청되지 않았습니다. 창을 닫을 때마다 확인하도록 고쳤습니다.
- 명절 금액을 3배로 넣었더니 Precision이 0.591로 떨어져 "분포만 바뀐" 장면이 되지 않았습니다. 1.5배(Precision 0.735)로 줄였습니다(개발 중 실험).

**발표에서 같이 말할 한계**
- Recall 하한 0.95가 절대값이라, 운영 모델이 이미 하한 아래인 7월에도 더 나은 후보를 떨어뜨렸습니다. 팀 결정이 필요한 설계 질문입니다.
- v4는 Recall 0.953으로 하한을 근소하게 넘었고, 경보 비율 5.45%가 상한 6%에 가깝습니다.
- 후보는 v1의 트리거 기준을 그대로 이어받습니다. ②·③은 시뮬레이션이고, 정답이 즉시 들어온다고 가정합니다.
