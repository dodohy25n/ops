# CSV 배치 처리 기준 현황과 남은 작업

정리일: 2026-10-08. 사용자가 확인한 운영 방식, 저장소 코드, 기존 측정 문서와 추가 강의 PDF 「모델 서빙 및 AIOps 구성」(140쪽)을 기준으로 정리했습니다. 저장된 과거 검증 결과와 이번에 직접 확인한 내용을 구분합니다.

추가 진행: 이 문서의 초기 점검 이후 CSV FastAPI 서버·확인 화면·CORS·요청 로그·지표·Docker를 구현했고, 이어서 판정 창 감시·재학습·게이트 교체·대시보드 감시 화면·6개월 시연까지 연결했습니다(커밋 `dfabda7`, `2fea235`, `a2590dd`). 최신 실행 방법과 검증 범위는 [CSV 서버 가이드](FastAPI-CSV서버.md), 시연 결과는 [설계 지표](설계지표.md) 7절에 있습니다.

## 1. 입력과 처리 흐름

사용자는 일정 기간의 카드 거래가 들어 있는 CSV를 업로드합니다. 시스템이 CSV에서 카드별 거래 시퀀스를 만들고 해당 기간을 배치로 분석합니다.

```text
기간별 거래 CSV 업로드
  → 컬럼·값·카드 식별자·시간 순서 검증
  → 카드별 시간순 정렬, 최근 20건씩 시퀀스 생성
  → 저장된 스케일러와 모델로 거래별 이상거래 점수·판정 계산
  → 분포 변화(PSI) 및 정답이 있는 거래의 Precision·Recall 집계
  → 지속적인 성능 저하 여부 판단
  → 조건 충족 시 fine-tuning
  → 별도 홀드아웃에서 배포 게이트 평가
  → 통과하면 모델·τ 교체, 실패하면 기존 운영 모델 유지
```

CSV 업로드가 외부 입력 단위이고, 20건 시퀀스는 시스템 내부의 모델 입력 단위입니다. CSV 전체가 정확히 20행이어야 하는 것은 아닙니다. 현재 모델은 같은 카드의 최근 20건 중 마지막 거래를 판정합니다.

기간 시작 부분을 판정하려면 카드별 직전 19건의 이력이 필요합니다. 현재 데이터 준비 코드는 운영 구간에 그 이력을 함께 저장합니다. 업로드에서도 과거 이력을 포함하거나 저장된 이력과 연결해야 합니다. 이력이 부족하면 해당 거래를 판정에서 제외하고 제외 건수를 결과에 표시하는 처리가 필요합니다.

PSI는 정답 없이 계산할 수 있습니다. Precision·Recall과 지도학습에는 정답이 필요합니다. 이번 시연에서 CSV에 정답을 함께 제공한다면 정답이 즉시 확정된다는 시뮬레이션 가정을 명시합니다. 정답과 이상거래유형·설명은 모델 입력 피처에 넣지 않습니다.

여기서 FastAPI 연결은 CSV 업로드·분석 실행·결과 조회를 모델과 연결하는 작업입니다. 초기 학습용 CSV와 이후 운영 분석용 CSV의 역할도 구분해야 합니다. 운영 CSV를 업로드할 때마다 스케일러를 새로 fit하거나 모델을 처음부터 학습하지 않습니다.

## 2. 현재 구현 상태

| 영역 | 확인한 상태 |
|---|---|
| 데이터 전처리 | 카드별 정렬, 17개 피처, 20건 시퀀스, 시간 분할 구현 |
| 모델 | LSTM 32 → 32 → 16, sigmoid 출력, binary crossentropy 학습 코드 구현 |
| 기준값 측정 | τ·성능 지표·감시 기준·PSI 기준 분포를 측정하는 코드와 결과 존재 |
| MLflow | v1을 Registry 버전 1로 등록하고 `champion` 지정. 후보는 게이트 통과 시에만 `champion`으로 교체 |
| 모델 로딩 | 같은 버전의 모델·스케일러·τ 로딩, 재로딩 실패 시 기존 캐시 유지 구현 |
| CSV 업로드·분석 서버 | 카드 거래 CSV 업로드·검증·배치 판정·결과 저장·조회 구현. 실제 v1으로 분석 확인 |
| 운영 감시·재학습 | CSV 분석마다 1,000건 창 감시·PSI 알림·2개 창 연속 미달 시 백그라운드 재학습 → 게이트 → 통과 시 champion 교체·창 초기화까지 연결. 서버 재시작 시 중단된 재학습 상태 복구. 테스트 45개 통과 |
| Docker·대시보드·시연 | 대시보드가 판정 창·PSI·재학습·게이트 결과를 표시. 2024년 하반기 6개월 시연에서 후보 3개 중 1개(10월 v4)가 통과해 교체. 같은 시연을 `model-runtime` 컨테이너에서 돌려 월별 결과가 같음을 확인(`bash backend/scripts/demo_docker.sh`) |

HAIC 주가 실습에서 가져온 감시·재학습 모듈은 카드 구조와 맞지 않아 삭제하고, 카드 거래용 감시(`monitoring/drift_monitor.py`)와 fine-tuning(`retrain.py`)을 새로 만들었습니다.

로컬 작업 폴더에는 원본 데이터, 전처리 데이터, `fraud_v1.keras`, `scaler.pkl`, MLflow DB가 있습니다. 이 파일들은 Git에서 제외하므로 복제한 환경에서는 실행 명령으로 다시 만듭니다.

## 3. v1과 배포 게이트의 역할

| 항목 | 2024년 상반기 측정값 |
|---|---|
| τ | 0.28 |
| Recall | 0.9519 |
| Precision | 0.7700 |
| F2 | 0.9089 |
| 경보 비율 | 4.4472% |

v1은 운영을 시작하는 기준 모델이므로 게이트 없이 `champion`으로 등록했습니다. 배포 게이트는 재학습한 후보 v2를 내보내도 되는지 판단할 때만 사용합니다.

배포 게이트는 후보와 현재 운영 모델을 같은 홀드아웃에서 평가해 Recall ≥ 0.95, 경보 비율 ≤ 6%, 운영 모델 대비 F2 회귀 없음을 검사합니다. 정상 거래가 존재하고 전체 1,000건·실제 이상거래 20건 이상인 평가 표본도 필요합니다.

홀드아웃은 fine-tuning과 τ 선택에 쓰지 않은 최근 구간에서 떼어 둡니다. 조정에 사용한 데이터로 다시 합격 여부를 판단하면 점수가 낙관적으로 나오기 때문입니다.

## 4. 링크 기획서와 로컬 설계의 차이

| 항목 | 링크 기획서 | 최신 로컬 문서·코드 |
|---|---|---|
| 거래 규모 | 약 217만 건, 확인 전 | 분석 기록: 1,952,871건, 이상거래 3.69% |
| 입력 길이 | N 미확정 | 20건, 피처 17개 |
| PSI 경고 시 대응 | 성능 기준을 평균 − 1σ로 좁힘 | 해당 규칙 제거. 항상 평균 − 2σ와 2개 창 연속 조건 사용 |
| 배포 경보량 제한 | Precision 하한 `P_min` | 경보 비율 6%를 직접 검사. `P_min`은 참고값 |
| 구현 범위 표현 | 감시·자동 재학습·롤백을 현재 구현으로 표현 | 감시·자동 재학습·게이트 교체까지 구현·시연. 롤백은 미구현 |

로컬 문서에서는 −1σ 기준이 정상 기간에 잘못된 재학습을 15회 일으켰고 −2σ와 연속 조건은 0회였다고 기록합니다. 이것이 −1σ 규칙을 제거한 근거입니다.

추후 기획서를 갱신할 때 위 차이와 CSV 입력 방식을 반영해야 합니다. 링크의 외부 문서는 이번에 수정하지 않았습니다.

## 5. PSI 문제와 수정 (완료)

처음 구현한 `psi_reference()`는 모든 피처에 분위수 구간을 사용했습니다. 0이 대부분인 이진 피처에서는 경계가 `[0.0]` 하나로 줄고, 기본 `np.digitize()` 처리로 0과 1이 같은 구간에 들어갔습니다. 그래서 작은 배열로 확인했을 때 양성 비율이 1%에서 50%로 바뀌어도 PSI가 0이었고, 당시 해외 여부·할부의 정상 창 PSI 0은 감시가 유효하다는 근거가 될 수 없었습니다.

이 문제를 고치기 위해 범주형 3개(해외 여부, 가맹점 매출 구간, 할부 여부)는 값별 비율로, 수치형(승인 금액, 승인 시간대, 사기 확률)은 기존 10분위 구간으로 계산하도록 바꾸고 기준 분포를 다시 측정했습니다(커밋 `a1b5631`). 수정 후 같은 1% → 50% 변화는 경고 기준 0.25를 넘고(`backend/tests/test_psi.py`), 재측정한 정상 창 PSI 최댓값은 금액 0.0652, 시간대 0.0793, 해외 0.0157, 가맹점 매출 구간 0.0362, 할부 0.0182, 사기 확률 0.0362로 모두 주의 기준 0.1 미만입니다(`thresholds.json`). τ와 게이트·트리거 기준은 재측정 후에도 같습니다.

사기 확률의 PSI 기준 분포는 2024년 상반기 검증 점수이며, [설계 지표](설계지표.md) 5-2절에 기준 기간과 그 한계를 명시했습니다.

결정한 세부값: 판정 창은 겹치지 않는 1,000건 단위, 재학습 데이터는 정답 있는 최근 40,000건, 재학습 요청·실행 중에는 새 요청을 만들지 않습니다. 분석 결과와 감시 기록에는 사용한 모델 버전과 τ를 함께 남깁니다. 기간 경계 이력은 업로드 CSV에 직전 19건을 포함하는 방식이며, 다른 업로드의 이력을 자동으로 합치지는 않습니다.

## 7. 팀 결정이 필요한 사항

6개월 시연(근거: [시연 실행 로그](results/시연-실행-로그.txt))에서 드러난 설계 질문을 한곳에 모읍니다. 현재 코드는 각 항목의 "현재 동작"대로 움직입니다.

| 번호 | 사항 | 무엇이 문제인가 (원인 → 결과) | 현재 동작 | 선택지 |
|---|---|---|---|---|
| 1 | **절대 Recall 하한이 더 나은 후보를 막음** | 게이트의 Recall 하한 0.95는 절대값입니다. 그래서 운영 모델이 이미 하한 아래로 떨어진 상황에서도 후보에 0.95를 요구합니다. 7월 후보 v2는 홀드아웃에서 F2 0.866으로 운영 모델 0.839보다 나았고 Recall도 0.923 대 0.869로 높았지만, 0.95에 못 미쳐 떨어졌고 더 나쁜 v1이 계속 판정했습니다 | 엄격한 하한 유지 | ① 그대로 유지(사기를 더 놓칠 수 있는 모델은 절대 내보내지 않음) ② 운영 모델이 하한 아래일 때는 "Recall과 F2가 모두 운영 모델 이상"이면 허용 ③ 하한 미달 후보는 자동 교체 대신 운영자 승인 대기 |
| 2 | **v4의 얇은 여유** | 10월 후보 v4는 Recall 0.953으로 하한 0.95를 0.003 넘었습니다. τ가 0.16으로 낮아지면서 홀드아웃 경보 비율 5.45%가 상한 6%에 가까워졌습니다. 다음 드리프트 때 경보 상한부터 막힐 수 있습니다 | 통과 후 그대로 운영 | ① 그대로 두고 경보 비율을 감시 항목에 추가 ② 경보 상한 6%(가정)를 탐지팀 실제 처리량으로 다시 정함 |
| 3 | **감시 기준 승계의 한계** | 후보는 v1의 트리거 기준(평균 − 2σ: Precision 0.6290, Recall 0.8632)과 거래 피처 PSI 기준을 그대로 씁니다. 후보의 정상 흔들림이 v1과 다르면 기준이 너무 느슨하거나 엄격해질 수 있습니다 | 승계(사기 확률 PSI 기준만 다시 잼) | ① 그대로 유지 ② 승격 후 첫 N개 창으로 기준을 다시 재는 절차 추가 |
| 4 | **롤백 미구현** | 게이트를 통과한 모델도 운영 데이터에서 실패할 수 있습니다. 지금은 승격 직후 다시 2개 창 연속 미달이면 새 재학습만 요청되고, 이전 버전으로 되돌리지는 않습니다 | 미구현 | ① 승격 후 일정 창 안에 재트리거되면 이전 champion으로 되돌림 ② 운영자가 MLflow에서 별칭을 수동으로 되돌리는 절차를 문서화 |
| 5 | **정답 즉시 도착 가정** | 시연 CSV에 정답이 함께 들어 있어 판정 직후 Precision·Recall을 계산합니다. 실제로는 고객 신고·탐지팀 확인으로 정답이 늦게 확정되므로, 성능 트리거가 늦어집니다 | 시연 가정으로 명시 | ① 발표에서 가정으로 밝힘(현재) ② 정답 도착 시점을 반영해 창을 늦게 닫는 방식 설계 ③ PSI 경고 시 운영자 점검 절차 추가 |

근거: 1·2는 시연 실행 로그의 7월·10월 재학습 결과, 3은 `backend/serving_app/retrain.py`와 [설계 지표](설계지표.md) 6절, 4는 설계 지표 6절, 5는 설계 지표 5-1절입니다.
